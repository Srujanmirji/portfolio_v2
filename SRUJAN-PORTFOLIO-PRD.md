# PRD, Srujan Mirji Portfolio V2

## 1. Product Overview

### Product Name

Srujan Mirji Portfolio V2

### Website

https://www.srujanmirji.in/

### Product Type

Premium interactive personal portfolio and personal-brand website.

### Primary Goal

Create a portfolio that feels like a high-end digital product and communicates Srujan's identity as an AI-focused software developer, product builder, and creative technologist.

The website must use scroll-driven storytelling as a core interaction.

The experience should make visitors want to continue scrolling while still making Srujan's work, capabilities, achievements, and contact information easy to understand.

---

## 2. Product Vision

The portfolio should answer three questions within the first minute:

1. Who is Srujan?
2. What does Srujan build?
3. Why should someone continue exploring or contact him?

The website should feel:

- Premium
- Experimental
- Modern
- Technical
- Editorial
- Personal
- Fast
- Intentional

The site should not feel like a template, resume, or generic developer portfolio.

---

## 3. Target Audience

### Primary

Recruiters and hiring managers looking for software, AI, or product talent.

### Secondary

Potential freelance clients and startup founders.

### Tertiary

Developers, designers, hackathon organizers, community members, and other technical people.

---

## 4. User Goals

Users should be able to:

- Understand who Srujan is.
- See his strongest projects.
- Explore detailed project case studies.
- Understand his technical capabilities.
- See his hackathon and community experience.
- Explore experimental work.
- Contact him quickly.
- Navigate the site without confusion.

---

## 5. Business and Personal Goals

The portfolio should help Srujan:

- Build a strong personal brand.
- Generate freelance opportunities.
- Attract internships and jobs.
- Demonstrate technical depth.
- Demonstrate product thinking.
- Demonstrate UI/UX and interaction skills.
- Showcase hackathons and projects.
- Stand out from conventional student portfolios.

Scrolling is the primary navigation mechanism.

The page should use scroll position to control:

- Typography
- Images
- Horizontal movement
- Scale
- Depth
- Section transitions
- Progress
- WebGL effects
- Project presentation

Animations must have narrative purpose.

Avoid excessive animation where the only effect is fading elements into view.

# 9. Hero Requirements

## Visual

Full viewport.

Black background.

Large typography.

Optional portrait or abstract visual.

Orange accent element.

Subtle grain.

## Content

SRUJAN
MIRJI

AI Engineer · Product Builder · Developer

SCROLL TO ENTER

## Interaction

Hero should be pinned for approximately 150vh to 220vh.

Scroll behavior:

### 0%

- Identity appears.
- Minimal navigation.
- Background is almost completely black.

### 20%

- Typography increases in scale.
- Second line enters.

### 40%

- Hero visual appears.
- Orange accent expands.

### 60%

- Supporting description appears.

### 80%

- Typography compresses.
- Navigation becomes persistent.

### 100%

- Hero releases into About.

# 22. Motion Requirements

## Animation Engine

GSAP + ScrollTrigger.

## Required Motion Types

- Scroll scrub
- Pinning
- Horizontal translation
- Scale
- Parallax
- Clip-path reveals
- Typography transforms
- Depth changes
- Cursor interaction
- Hover transitions

## Motion Rules

Animations must:

- Be smooth.
- Be reversible.
- Respond naturally to scroll.
- Avoid layout thrashing.
- Use transform and opacity where possible.
- Respect reduced-motion preferences.

## Reduced Motion

When `prefers-reduced-motion` is enabled:

- Disable major parallax.
- Reduce scrub effects.
- Remove heavy WebGL motion.
- Keep content fully accessible.
- Use simple transitions.

---

# 23. WebGL Requirements

WebGL should enhance the experience.

It must not become the experience itself.

Potential uses:

- Hero visual
- Background distortion
- Project transitions
- Contact visual

Avoid:

- Constantly moving objects
- Heavy particle fields
- Random 3D objects
- WebGL behind every section

# 25. Responsive Requirements

## Desktop

Full experience.

Use horizontal scroll, pinned sections, WebGL, cursor interactions, and large compositions.

## Tablet

Preserve core storytelling.

Reduce WebGL complexity.

Reduce extreme typography.

## Mobile

Do not simply scale down desktop.

Use vertical storytelling where horizontal interaction becomes awkward.

Reduce:

- WebGL
- Parallax
- Large transforms
- Complex cursor effects

Keep:

- Typography hierarchy
- Project storytelling
- Progress
- Navigation
- Case studies

# 32. Content Management

Keep portfolio content data-driven.

Project data should live separately from UI components.

Example:

```ts
{
  slug: "studentsmate",
  title: "StudentsMate",
  description: "AI-powered academic platform for students.",
  categories: ["AI", "Education", "Web App"],
  technologies: ["Next.js", "React", "Supabase"],
  featured: true
}
```

This allows projects to be added or updated without rewriting layout components.

---

# 33. Loading Experience

Initial load should have a short branded loading state.

Example:

SM

Avoid long artificial loading screens.

The page should become interactive as soon as practical.

---

# 34. Error and Fallback Behavior

If WebGL fails:

- The website must still work.
- Replace WebGL visuals with static imagery or gradients.
- Keep all content accessible.

If an image fails:

- Use a neutral fallback.
- Do not break the layout.

If JavaScript is delayed:

- Basic content should remain structurally understandable.

---

# 35. Security

- No secrets in client code.
- No exposed API keys.
- Validate contact form input.
- Rate-limit server-side contact submission if implemented.
- Sanitize user-provided content.
- Avoid unnecessary third-party scripts.

# 37. Non-Goals

Do not turn the portfolio into:

- A social network
- A blog platform
- A CMS-heavy application
- A giant 3D demo
- A technology logo showcase
- A resume PDF replacement
- A collection of unrelated animations

The primary product is an interactive personal portfolio.

---

# 38. Success Criteria

The redesign succeeds if:

1. Visitors immediately understand who Srujan is.
2. Visitors understand what he builds.
3. Visitors explore multiple projects.
4. Visitors can reach a project case study within one or two interactions.
5. Visitors can contact Srujan quickly.
6. The experience feels memorable without sacrificing usability.
7. The site demonstrates both engineering and product/design ability.
8. The experience remains smooth on modern desktop hardware.
9. Mobile remains usable and visually coherent.
10. The site feels custom-built rather than template-based.

---

# 39. Final Product Principle

The portfolio itself is part of Srujan's portfolio.

The website should demonstrate the qualities it claims:

If Srujan says he builds products, the website should feel like a product.

If Srujan says he understands interaction, scrolling should demonstrate it.

If Srujan says he works with modern technology, the implementation should demonstrate technical quality.

If Srujan says he cares about design, every spacing, transition, type scale, image, and interaction should support that claim.

Build the experience with restraint, precision, and strong art direction.
